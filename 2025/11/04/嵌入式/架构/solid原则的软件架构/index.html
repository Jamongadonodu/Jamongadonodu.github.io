基于solid原则的面向对象MCU平台化软件架构

文章发布时间:
2025-11-04

最后更新时间:
2025-11-13

传统的MCU开发常陷入“面向过程”或“硬件寄存器操作”的泥潭，导致代码高度耦合、难以复用和测试。我们的目标是构建一个：面向对象, 平台化, SOLID化的软件架构

架构设计

核心目标

  • 平台化：可迁移，可测试，可维护
  • 接口
  • 抽象：太高->失细节 太低->难迁移
  • 迁移测试：接口可注入，可Mock, 可验证

接口定义思路

  • 接口是契约，不是函数集合
  • 每个接口需要明确
    • 输入/输出
    • 阻塞/非阻塞
    • 错误码
    • 功耗影响
  • 所有依赖（i2c,delay）必须注入，不能用硬编码

做单元测试时，可替换为Mock，迁移时注入新实现

依赖注入

模块不创建依赖，而是外部传入

  • Handler 不依赖HAL，而是依赖接口表
  • MCU/OS层只负责实现这些接口
  • 可替换，可Mock,可测试
  • 平台迁移时，只修改注入，不改逻辑

solid设计原则

solid设计是面向对象的原则，是由Gang of Four（四人帮），即Erich Gamma, Richard Helm,Ralph Johnson & John Vlissides四人）的《设计模式》（1995年出版）是第一次将设计模式提升到理论高度，并将之规范化。

单一原则（Single Responsibility Principle）

一个类只负责一件事情。价值：高内聚，低耦合，拓展性和健壮性强。
核心：一件事一个模块

C语言中，就是一个结构体在设计和封装的时候只负责一个事情

应用：

  • 驱动
  • UI
  • 存储
  • 分层

开闭原则（Open Closed Principle）

软件中的对象（类、模块、函数等）应该满足对于拓展是开放的，对修改是封闭的。
核心：拓展不修改旧逻辑

应用：

  • 注册新设备
  • 加设备不该旧逻辑

里氏替换原则（Liskov Substitution Principle）

简单来讲就是子类可以去拓展父类的功能，但不能改变父类原有的功能。
核心：行为一致可替换

应用：

  • mpu和wit无需修改app

接口隔离原则（Interface Segregation Principle）

不应该强迫用户端实现一个它用不上的接口
核心：精准依赖

应用：

  • 前向声明
  • 不暴露相关接口

依赖倒置原则（Dependency Inversion Principle）

高层次模块不应该依赖测层次的模块，实际上是面向抽象编程思想，这样可以降低代码间的耦合度，使其看扩展、易维护。
核心：依赖抽象

应用：

  • app代码依赖函数表而非HAL库

这些原则属于建议性原则，大家在做架构设计的时候要从实际的业务角度出发，切记不要为了设计而设计（冗余设计）。

与linux的关系

  • linux：一切皆文件 -> 抽象统一但损失实时/功耗细节
  • 嵌入式：介于HAL和linux
    • 保留回调/异步/低功耗控制
    • 同时提供统一接口风格

接口测试策略

  • 单元测试： Mock HAL验证逻辑
  • 接口测试：验证通信正确性
  • 集成测试：验证事件流，功耗逻辑
  • 迁移测试：验证接口在新MCU的一致

总结

平台化不是分层多，而是接口稳

  • 稳定的接口 -> 可迁移
  • 可注入的依赖 -> 可测试
  • 遵循solid -> 可演化

平台化平台架构

MCU Platform

用户接口层

  • 向上暴露与MCU相关的服务，系统复位，时钟切换，进入和退出低功耗模式，喂硬件看门狗，获取系统tick等
  • 上层（App/Middleware）不直接调用寄存器，而是调用这些接口

管理层

  • Bootloader/App分区管理
  • OTA升级状态标志位（在EEPROM或配置区）
  • 回滚及双区固件搬运策略（ A/B区+校验+回退）
  • 日志存取（错误栈/硬fault信息/Log）

内核支持层

  • 时钟树/PL初始化
  • 中间向量表重定位（Bootloader->App）
  • SRAM加速路径的SCT分散加载
  • MPU配置（内存保护，捕获数组越界等）

测试支持层

  • 上电自检：校验固件完整性
  • 健康状态导出接口，用于线测试工具快速验证核心外设（i2c,spi,dma,uart）和flash可写性

外设驱动层

  • 针对片上外设(i2c,spi,adc,uart,tim/pwm,dma,gpio等)提供统一HAL访问接口
  • 这些接口作为Driver层的基础

OS Platform

系统管理层

  • freeRTOS内核配置（抢占/优先级/定时器/内存分配策略）
  • Tickless模式策略
  • 任务优先级整体规划和统一表

OS抽象层

  • 提供统一的任务/队列/互斥锁/事件组/Notify API
  • 任务看门狗登记/喂狗接口
  • Idle钩子统一处理（降频，功耗统计）

测试支持层

  • SystemView/Trace Hook
  • 栈水位检测/任务运行时统计接口
  • 覆盖率/活性检查（是否有任务饿死）

外设驱动层

  • 用于将中断事件安全的转交到线程世界的“中断转发机制”（eg：MPU6050的中断ISR里面发Notify唤醒处理线程）
  • OS定时器封装（功耗超时等）

BSP Platform

驱动实例层（Driver）

  • 具体外设驱动:MPU6050,NFC模块，LCD屏幕……
  • 驱动关注“怎么和MCU交流”（i2c/spi/uart/pwm/adc等）,以及基本的数据拿取

抽象接口层

  • 高层业务驱动管理层
  • 提供异步接口，回调注册，数据新鲜度，缓冲和滤波
  • 负责避免资源冲突（多任务同时读取统一i2c总线），负责节电（按需采样），负责错误修复（i2c reset重试）

测试支持层

  • 提供标准的自检API（eg：读取一次数据的返回值/状态码）
  • 工装夹具可调用这些接口做产线校准（写入校准系数到flash）

Middleware Platform

交互接口层

  • UI桥接
  • BLE透传/OTA命令接收接口
  • 与APP对接的高层服务层

数据处理层

  • 反馈数据处理
  • 传感器校准系数应用
  • 误差补偿

系统支持层

  • 存储抽象（config，固件分区，日志区）
  • 日志/错误记录/回放
  • 看门狗策略与错误恢复协调

安全加密层

算法与显示器
